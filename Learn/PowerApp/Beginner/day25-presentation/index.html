Part 5 • Data Layer

Layer 3: Normalized Data Schema (SharePoint List)

SharePoint List: EquipmentWorkOrders — Every column exists to serve a human step.

📋 SharePoint List Columns

Column Name Data Type Role in Business Process
Title Single line of text Unique Work Order ID (e.g. WO-1045)
MachineID Choice CNC-01, CNC-02, CNC-03, Lathe-01
Priority Choice Critical, High, Medium, Low
Status Choice New, Dispatched, In Repair, Closed
RepairCost Number Dollar cost of parts for Sum()
AssignedTech Person Office 365 User Profile

🛡️ Why Normalization Protects the App

  • Why Choice for MachineID? If operators type free text, they type 'CNC4', 'cnc-04', 'Machine #4'. The filter Filter(WorkOrders, MachineID = 'CNC-04') will fail!
  • Why Choice for Priority? Guarantees sorting and color coding rules work 100% of the time without typos.
  • Why Number for RepairCost? You cannot calculate Sum(WorkOrders, RepairCost) on text fields!
  • Why Person for AssignedTech? Automatically retrieves user email, photo, and manager from Office 365.

Trainer Speaking Script & Pedagogical Cues:

Layer 3 Normalization (3 min): "Explain why choice fields are mandatory for machine names and priority. If operators type free text, they type 'CNC4', 'cnc-04', 'Machine #4'. The filter will fail! Choice columns enforce business discipline."

Part 5 • Screen Architecture

Layer 4: The Standard 3-Screen Enterprise Pattern

Never create 20 chaotic screens. 95% of all enterprise apps follow this exact 3-screen layout.

Screen 1 • Browse

scr_BrowseWorkOrders

The central shop-floor dashboard. Operators and leads find active work orders instantly.

• galWorkOrders.Items = Filter(...)
• Search bar by Machine ID
• + New Work Order button (Navigates to Screen 2)
Screen 2 • Create

scr_CreateWorkOrder

A clean, distraction-free intake form for shop-floor operators to report breakdowns.

• frmCreateOrder.DataSource = WorkOrders
• Mode = FormMode.New (wipes cards blank)
• Submit button with validation lockout
Screen 3 • Detail & Edit

scr_DetailEditWorkOrder

The technician workbench. Reads existing incident details and records repairs.

• Item = galWorkOrders.Selected
• Mode = FormMode.Edit (updates existing row)
• ResetForm() cancel escape hatch

Layer 4 3-Screen Pattern (3 min): "Explain why 3 screens is the golden standard. Screen 1 lets you find and browse. Screen 2 gives you a clean slate to submit without distractions. Screen 3 gives technicians the full context of the selected record. It is clean, fast, and easy to maintain."

Part 6 • Decision Logic

Layer 5: Business Rules & Power Fx Decision Logic

Connecting human business rules to boolean conditions and reactive Power Fx properties.

⚙️ Business Rule → Power Fx Formula

Rule 1: Never Submit Empty Requests

Lock the submit button until machine and description are filled.

btnSubmit.DisplayMode = If(IsBlank(txtIssue.Text) Or IsBlank(cmbMachine.Selected), DisplayMode.Disabled, DisplayMode.Edit)
Rule 2: Highlight Critical Alarms

Tag pill turns red if Priority is Critical.

tagPriority.Fill = If(ThisItem.Priority.Value = "Critical", ColorValue("#ef4444"), ColorValue("#06b6d4"))

🔒 The 3 Essential Architectural Formulas

  • Condition Chain: Every formula asks a question ➔ evaluates True/False ➔ triggers an action.
  • Form Binding: frmDetail.Item = galWorkOrders.Selected guarantees zero duplicate records during editing.
  • Safe Cancellation: ResetForm(frmDetail); Back() discards memory buffer changes without polluting records.

Trainer Speaking Script & Pedagogical Cues:

Layer 5 Logic (3 min): "Break down the formula structure. Plain-English condition ➔ Question ➔ True/False result ➔ Action. Show how btnSubmit.DisplayMode uses If(IsBlank(...)) to physically prevent empty records."

Part 7 • Storage & Verification

Layers 6 & 7: Cloud Storage & User Feedback Hooks

How data commits to SharePoint and how users receive verified reactive confirmation.

Layer 6: Cloud Storage

Executing Writes via SubmitForm()

When the operator taps Save, SubmitForm(frmOrder) inspects Form.Mode:

  • If New: Generates HTTP POST ➔ Creates new row & new SharePoint ID.
  • If Edit: Generates HTTP PATCH ➔ Updates existing row matching Item.ID without duplicating!
Layer 7: Feedback Hooks

Event Hooks: OnSuccess & OnFailure

// frmOrder.OnSuccess
Notify("Work order saved to cloud!", NotificationType.Success);
Navigate(scr_BrowseWorkOrders)
// frmOrder.OnFailure
Notify("Save failed: " & frmOrder.Error, NotificationType.Error)

Trainer Speaking Script & Pedagogical Cues:

Layers 6 & 7 (3 min): "Clarify that SubmitForm() does the heavy lifting. But highlight the event hooks: OnSuccess runs only when SharePoint confirms the write! Never put Notify() inside the button's OnSelect—if the internet is disconnected, the button will lie and say 'Success!' even though data was lost."

  • BrakeCheck (Choice): Pass, Fail

  cmbBrakes.Selected.Value = "Fail" Or numBattery.Value < 20,

Part 12 • Misconception Busting

3 Beginner Architectural Misconceptions Demolished

Unlearning beginner fallacies to build resilient, maintainable enterprise software.

Fallacy 1

"Build the UI First"

The Trap: Opening Power Apps Studio to drag buttons and pick nice colors.

The Truth: UI built without data schemas gets deleted 100% of the time. Design data first!

Fallacy 2

"Use Text for Everything"

The Trap: Making all SharePoint columns 'Single line of text' for laziness.

The Truth: You destroy sorting, ruin Sum() calculations, and allow typos to corrupt filters.

Fallacy 3

"More Screens = Better App"

The Trap: Creating 20 separate screens for every small variation.

The Truth: Master the 3-Screen Pattern. It handles 95% of business workflows with zero bloat.

Trainer Speaking Script & Pedagogical Cues:

Misconception Review (3 min): "Debunk the 3 myths: (1) UI first, (2) Text for everything, (3) 20 screens. Modern app development is about simplicity, discipline, and maintainability."

Part 13 • Deep Review

The 5 Architectural Golden Rules Summary

Key takeaways every enterprise developer must memorize before building.

🔑 Rules 1, 2, and 3

  • Rule 1 (Problem First): The business problem determines the human decisions, which dictates what data facts must be recorded.
  • Rule 2 (Typed Columns): Never store numbers or dates as text. Correct data types enable sorting, Sum(), and validation.
  • Rule 3 (3-Screen Pattern): Standardize on Browse ➔ Create ➔ Detail/Edit for 95% of business applications.

🔑 Rules 4, 5 and Core Axiom

  • Rule 4 (OnSuccess Hooks): Put user notification inside Form.OnSuccess, never inside the button's OnSelect!
  • Rule 5 (Logic Controller): Power Fx asks questions, evaluates True/False, and directs reactive actions safely.
  • Core Axiom: 10 minutes of architectural drafting on paper saves 10 hours of deleting bad controls in Power Apps Studio.
