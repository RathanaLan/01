Part 1 • Why This Exists

Workplace Crisis: The "Vanishing Reports" at Apex Plastics

The \$42,000 breakdown that proved why apps require persistent cloud data vaults.

The Incident Friday, 4:45 PM

Extruder Line 3 Motor Overheating

Operator Sarah noticed high vibration and burning smell on Extruder Line 3. She dutifully opened her new Power App, typed the warning, and tapped Submit.

Because the app only saved the ticket into a Day 18 variable (Set(varLastTicket, ...)), the data was held in her tablet's memory. At 5:00 PM, she powered down her tablet and went home.

The Result on Monday Morning:

Maintenance arrived with zero tickets. The motor seized at 6:15 AM. 14 hours of production lost. Total damage: \$42,000.

Architectural Root Cause

Memory Volatility vs. Enterprise Persistence

Flaw 1: Variable Scope is Single-Session

Variables die when the session terminates. They cannot survive an app restart.

Flaw 2: Zero Cross-Device Sharing

Sarah's tablet could not communicate with the maintenance supervisor's desktop.

The Fix: SharePoint List Cloud Repository

SharePoint writes every record immediately to Microsoft data centers with geo-redundancy and instant multi-user synchronization.

Trainer Speaking Script & Pedagogical Cues:

Deliver with Drama: "Make the story vivid. Sarah did nothing wrong! She followed instructions. The ARCHITECT made the mistake of confusing temporary memory with permanent storage. When you design an app, lives and plant safety depend on data actually reaching the database."

Temporary RAM (Day 18 Variables)

  • Stored in local device memory chips (RAM).
  • Accessible ONLY to the current app session.
  • Disappears immediately on browser refresh or app close.
  • Zero audit trail, zero backup, zero sharing.

Persistent Cloud Vault (SharePoint List)

  • Stored on high-availability Microsoft 365 cloud servers.
  • Simultaneously accessible by hundreds of licensed team members.
  • Permanent survival: survives tablet reboots, app uninstalls, and device loss.
  • Built-in version history, created-by audit stamps, and security permissions.

Trainer Speaking Script & Pedagogical Cues:

SharePoint Vocabulary Glossary

SharePoint List:

A structured collection of data rows. Similar to an Excel spreadsheet, but with strict database rules, security, and cloud APIs.

A single data property with an enforced type (e.g., Department must be a Choice, Date must be a Date).

Item / Record:

A horizontal row in the list representing one specific incident, maintenance request, or customer order.

Part 2 • Column Anatomy

Column Anatomy 1: The Sacred "Title" Column

Understanding why SharePoint mandates one special primary text column in every list.

The Unbreakable Rule of SharePoint

Every time you create a SharePoint list in Microsoft 365, SharePoint automatically creates a default column called Title.

WARNING: You CANNOT Delete the Title Column!

If you try to delete it in SharePoint settings, there is no Delete button. It is the architectural anchor used by Microsoft search, indexing, and mobile views.

Beginners often panic because they don't have a field named "Title". They try to create a second column called "Ticket Number" and leave "Title" blank, which creates errors!

The Professional Best Practice: Rename It!

Instead of fighting SharePoint, adopt the industry standard pattern: Rename its display name to match your primary identifier!

For Maintenance Apps:

Rename Title → Ticket ID (e.g., TKT-1001)

For Asset Tracking Apps:

Rename Title → Serial Number (e.g., SN-99482)

For HR Expense Apps:

Rename Title → Claim Reference (e.g., EXP-2026-04)

Trainer Speaking Script & Pedagogical Cues:

Emphasize the Golden Rule: "Write this on the physical whiteboard or highlight it strongly: 'NEVER FIGHT THE TITLE COLUMN. RENAME IT TO YOUR TICKET ID.' If a student ever comes to you saying their app is failing to save, 90% of the time they left the Title column blank because they didn't know it was required."

Part 2 • Column Anatomy

Column Anatomy 2: Choice Columns & Controlled Vocabulary

Eliminating typos and reporting disasters by enforcing fixed dropdown selections.

The Disaster of Free-Text Columns

Suppose you make the Department column a standard "Single Line of Text". Five different operators type in their department:

Row 1: "Molding"
Row 2: "molding" (lowercase)
Row 3: "Moulding" (British spelling)
Row 4: "Moldng" (typo)
Row 5: "Plastic Molding Dept" (verbose)

When the Plant Manager asks: "How many breakdowns happened in Molding this month?", Power Apps and Power BI see 5 completely different departments! Your monthly report is ruined.

The Solution: SharePoint Choice Columns

A Choice column locks the options into a strict, validated list. Users can only select from authorized options:

Department Choices:

Molding, Extrusion, Packaging, Quality, Maintenance

Urgency Level Choices:

Low, Medium, High, Critical

Status Choices:

New, In Progress, Resolved

Trainer Speaking Script & Pedagogical Cues:

Interactive Question: "Ask the class: 'What happens in Excel when 10 different people type the name of a supplier?' The class will laugh and say: 'Chaos!' Tell them: 'In professional software, we eliminate human typing errors at the database layer using Choice columns.'"

Part 2 • Column Anatomy

Column Anatomy 3: Date/Time, Numbers & Multi-Line Text

Selecting the exact right column type for every business data attribute.

Date & Time

ReportedDate

Stores standardized calendar timestamps.

  • Format: Date Only vs. Date & Time.
  • Default Value: Today's Date.
  • Allows chronological sorting and SLA calculations (e.g., tickets open > 24h).
Multiple Lines of Text

ProblemDescription

Allows paragraphs up to 63,999 characters.

THE RICH TEXT TRAP:

ALWAYS pick Plain Text! Rich Text injects ugly HTML tags like <div> into your Power Apps inputs!

Number

DowntimeMinutes

Strictly enforces numerical values.

  • Prevents typing letters like "twenty".
  • Allows mathematical calculations: Sum(), Average().
  • Can set minimum and maximum constraints (e.g., 0 to 1440 mins).

Trainer Speaking Script & Pedagogical Cues:

Emphasize the Plain Text Warning: "I want everyone to look at the center card. When creating a Multiple Lines of Text column, SharePoint offers a radio button: 'Plain text' vs 'Use enhanced rich text'. You MUST choose Plain Text. If you pick Rich Text, your users will see messy HTML code inside Power Apps."

Part 5 • Common Traps

5 Dangerous Misconceptions vs. SharePoint Reality

Avoid the costly traps that break beginner Power Apps projects.

The Beginner Misconception

1. "I don't need Title, so I'll just delete it."

They get frustrated when SharePoint refuses to delete Title.

2. "Rich text is prettier for descriptions."

They pick Rich Text and end up with HTML junk inside their Power App.

3. "SharePoint List is just an Excel file in the cloud."

They treat it like Excel and accidentally break multi-user locking.

4. "Naming columns with spaces like 'Ticket Number' is fine."

SharePoint generates ugly internal names like Ticket_x0020_Number.

5. "Sharing the Power App automatically shares the list."

Users get permission denied errors because list permissions were forgotten.

The Production Architect Reality

1. Always RENAME Title to your primary ID.

Rename it to Ticket ID, Asset Tag, or Order Number.

2. ALWAYS select Plain Text for multi-line inputs.

Plain text cleanly integrates with Power Apps text input controls.

3. SharePoint is a true transactional cloud database.

It handles simultaneous multi-user writes without file corruption.

4. Create column names without spaces first, then rename display.

Creates clean, readable internal schemas for Power Fx formulas.

5. Grant Microsoft 365 security group permissions on the List.

App users must have at least 'Contribute' or 'Edit' rights on the list.

Trainer Speaking Script & Pedagogical Cues:

Highlight Trap #5: "Trap #5 is the #1 reason why corporate app rollouts fail on day one! The developer builds a fantastic app, shares it with 200 users, and all 200 users get a gray error screen saying: 'You don't have permission to view this list'. Always remember: Power Apps permissions and SharePoint list permissions are two separate keys to two separate doors!"
