Prerequisite Check: What We Already Know

Before building complete flows, let's verify our foundation from Days 5, 7, and 8.

Day 8 Concept

1. Workflow vs. Task List

"What is the core difference between a simple to-do list and a business workflow?"

CORRECT ANSWER:

A to-do list is an isolated list for one person. A workflow connects sequential steps, distinct status states, conditional decisions, and role-based handoffs across multiple people.

Day 8 Concept

2. Mutual Exclusivity

"Why must a workflow's Status have exactly ONE active value at any moment?"

CORRECT ANSWER:

Because an app's logic cannot govern permissions or UI screens if a record claims to be both "Submitted" and "In Progress" simultaneously. One single truth prevents chaos.

Days 5 & 6 Logic

3. The Decision Diamond

"What decides which direction a business flow takes when it reaches a fork in the road?"

CORRECT ANSWER:

A Condition Gate. It tests data against business rules (e.g., EstCost > 1000). If True, it routes down one path; if False, it routes down the other.

The $72,000 "Dropped Baton" Disaster at Apex Plastics

When every individual does their task, but the overall flow fails in the silence between people.

08:15 AM

Operator Bopha fills out a paper request for a jittering robotic servo motor arm and drops it into the supervisor's inbox.

09:00 AM

The Silent Gap: Maintenance assumed purchasing was ordering parts. Purchasing assumed engineering hadn't approved. The paper sat between trays.

Weekend

The Catastrophe: The un-serviced motor seized mid-stroke, shattering the injection mold die. Total replacement and downtime penalty: $72,000!

$72,000 Loss

The Root Cause: The Dropped Baton

Each person completed their individual action, yet the company suffered a catastrophe. Why?

  • ❌ No Connected Flow: Steps were isolated islands rather than a continuous chain.
  • ❌ No Visible Ownership: Nobody could see whose turn it was to hold the baton.
  • ❌ No Status Engine: The request sat invisible on a desk with zero system alerts.
"When no one knows who owns the next step, work dies in the silence between people."

Non-Linear Flow Architecture

Branching Paths: Happy Paths, Exits & Rework Loops

Real factories have unexpected outcomes. If your app only handles the happy path, it will fail in production.

Path 1: The Happy Path

Routine Direct Flow

Request is valid ➔ Supervisor approves ➔ Tech repairs ➔ QC passes ➔ Closed.

Result: Closed (Success)
Path 2: The Rejection Exit

Invalid / Duplicate Request

Supervisor identifies duplicate report or operator error. Enters mandatory reason.

Result: Rejected (Terminated)
Path 3: The QC Rework Loop

Tolerance Out of Spec

Repaired mold fails stamping test (Tolerance > 0.02mm). Loops back to Technician!

Loop: In Repair (Re-work)

💡 Why the Rework Loop is Essential:

If QC rejects a repair and the app simply marks it "Rejected", the technician cannot log additional hours or parts, and the operator must type a duplicate ticket from scratch. The Rework Loop keeps the exact same ticket ID alive so the full repair history is preserved!

Branching Architecture (35:00 – 40:00)

Spend extra time on the Rework Loop. This is where beginner developers usually make mistakes. Emphasize: a failed quality check should NOT terminate the ticket; it should loop back to the technician with a specific reason.

Power Fx Logic Interlocks

Enforcing the Flow in Power Apps Code

Real apps do not rely on user good behavior. Power Fx rules actively prevent illegal jumps.

Rule 1: Role-Based Approval

Requirement: Only Supervisors can see the 'Approve' button, and only when a ticket is actively 'Submitted'.

btnApprove.Visible = (UserRole = "Supervisor") && (Status = "Submitted")

Uses && (AND) so an operator cannot approve their own ticket, nor can an approval happen after work is closed.

Rule 2: Conditional Escalation

Requirement: If estimated cost exceeds $2,000, require Plant Manager approval; otherwise route to Maintenance Lead.

NextApprover = If(EstCost > 2000, "Plant Manager", "Maintenance Lead")

Evaluates the number condition to automatically choose the correct subsequent swimlane owner.

Rule 3: Immutability on Closure

Requirement: Once the QC inspector signs off and marks the ticket 'Closed', lock all inputs to prevent historical tampering.

frmTicket.DisplayMode = If(Status = "Closed", DisplayMode.View, DisplayMode.Edit)

Switches the entire form to read-only DisplayMode.View, protecting audit compliance and ISO records.

Power Fx Interlocks (43:00 – 45:00)

Break down the syntax calmly. Remind them: UserRole = "Supervisor" produces True or False. Status = "Submitted" produces True or False. && combines them. Exactly as we mastered on Day 6!

Pitfalls to Avoid

Four Dangerous Beginner Misconceptions

Recognize these plausible wrong mental models before they break your production applications.

Wrong Mental Model 1

"The Happy Path is the only path."

❌ "Everything will be approved smoothly and pass inspection on the first try."

✔️ Reality: 30% of requests are rejected, missing info, or fail quality checks. If your app lacks alternate branches, users revert to paper.

Wrong Mental Model 2

"Everyone should see every button."

❌ "I'll put Submit, Approve, and Close buttons on one screen so anyone can help."

✔️ Reality: Buttons must be governed by Role and Status. Operators should never see approval buttons; techs should never bypass QC.

Wrong Mental Model 3

"Status is just free-form text."

❌ "I'll give users a text box to type 'almost done' or 'waiting for parts'."

✔️ Reality: Power Fx logic formulas cannot evaluate typos like 'almst dun'. Status is an engine state managed by Choice sets.

Wrong Mental Model 4

"A business flow is an org chart."

❌ "My diagram shows CEO ➔ Manager ➔ Supervisor ➔ Worker."

✔️ Reality: An org chart shows power hierarchy; a business flow shows the journey of a specific piece of work over time.

Misconception Busting (70:00 – 75:00)

Highlight Misconception 3 especially: Free-form text for status is the #1 reason amateur apps collapse. Reiterate: Choice columns are mandatory for status fields.
