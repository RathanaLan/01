Prerequisite Retrieval: Locking In Prior Knowledge

From Day 10: Tables vs. Variables

"Why can't an enterprise ticketing system store requests in simple global variables?"

Correct Concept: A variable is a single box that holds exactly one value at a time. The moment a second employee submits a request, it overwrites the first request! We need a Table to hold hundreds of independent Records.
From Day 9: The Role of Status

"What is a 'Status' in a business flow, and why does Power Fx care about it?"

Correct Concept: Status is not decorative text; it is the traffic cop or switch of the application. Power Fx checks the Status (e.g. Status = "Submitted") to decide which buttons appear, who owns the work, and whether screens are editable or locked.
From Day 4: Condition Data Types

"If we store an estimated repair cost as plain text like '$500', what happens when Power Fx evaluates a condition?"

Correct Concept: Power Fx will fail or throw a type mismatch error! Computers cannot perform mathematical comparisons (>, <) on text characters with symbols. Numbers and Currency must be stored as Number data types!

Workplace Crisis Case Study

The $42,000 "47-Column Excel Monster" & The Chemical Leak

What happens when you design data from guesswork rather than from what the process requires.

Month 1
The Amateur Build: The plant manager asked a junior developer to build an app. The developer went around asking everyone: "What columns do you want?" They created a spreadsheet with 47 random fields, all formatted as free text!
14:10 PM
The Hazardous Leak: On Line 4, a toxic solvent pump seal failed. Operator Sothea typed: Machine: "Line 4 Main Pump", Priority: "EMERGENCY ASAP!!!", Cost: "high".
14:15 PM
The Squeaky Chair: In the front office, an operator typed: Machine: "Desk Chair", Priority: "urgent".
14:30 PM
The Data Chaos: The maintenance supervisor opened the list. Alphabetical sorting put "urgent" *before* "EMERGENCY ASAP!!!". Because there was no unique auto-ID, two tickets were numbered "#12". Maintenance dispatched a technician to the office chair!
18:00 PM
The Catastrophe: The unattended pump ruptured. 200 workers evacuated. Total hazmat cleanup and EPA penalties: $42,000!
$42,000 Loss

The Root Architectural Failure

The developer thought: "More columns and free text gives users more freedom."

⚠️ Unrestricted free text and random columns produce a digital landfill where critical alarms cannot be sorted, filtered, or automated!
The Architectural Fix:

Never ask "What columns do you want?" Ask: "What question must be answered at this step of the process?" Every field must have a strict Data Type, a clear Status role, and a unique immutable ID.

Data Type Selection

Choosing the Right Data Type: The 7 Core Building Blocks

Data types govern the shape of the data and what Power Fx calculations are legally allowed.

Text

Single Line of Text

Short strings under 255 characters. Names, short summaries, serial numbers.

Example: "Hydraulic seal leak"
Multi-Text

Multiple Lines of Text

Long descriptions, technician repair notes, troubleshooting histories.

Example: "Disassembled motor arm, replaced worn bearings..."
Number / Currency

Whole Number / Decimal

Quantities, repair hours, costs. Enables mathematical calculations (+, Sum, >).

Example: 450.00, 3.5 hours
Date & Time

Date and Time

Timestamps, submission dates, audit logs. Enables duration tracking (DateDiff).

Example: 2026-10-30 14:15
Choice (OptionSet)

Choice / Dropdown

Strict predefined list of options. Prevents typos and guarantees uniform sorting.

Example: ["Low", "Medium", "High", "Critical"]
Yes / No

Boolean (Two States)

Binary truth state. Direct input for IF conditions and safety interlocks.

Example: IsApproved = True

Data Types Explanation (30:00 – 35:00)

Emphasize: "Why do we have Choice columns instead of Text? Because if humans type 'High', 'high', 'HIGH', 'urgent', or 'hi', a computer sees five completely different words! A Choice column forces everyone to pick from the exact same pre-approved menu."

Data Integrity Standard

The Anatomy of a Unique ID: The Unchanging Birthmark

Why every enterprise record must have a permanent, system-generated identifier that never changes.

Bad Approach: Manual Typing

"Ticket #1", "Ticket #2"

  • ❌ Two operators create ticket #12 at the same time.
  • ❌ An operator typos "Ticket 14B" instead of "Ticket 14".
  • ❌ A user accidentally changes the ID to cover up a mistake.
  • ❌ Accounting cannot link purchase orders to repair jobs.
Result: Collisions, lost tickets, audit failure.
Enterprise Standard: Auto-Number

REQ-2026-0042

  • ✓ Prefix: Identifies business unit (REQ = Maintenance Request).
  • ✓ Year / Stamp: Prevents number overflow across decades (2026).
  • ✓ Sequential Digits: Guaranteed unique counter (0042).
  • ✓ Immutable: System generated at creation; read-only forever.
Result: 100% trace, zero duplicates, ISO compliant.

ID Immutability Protocol (40:00 – 45:00)

Ask: "Can you change your national passport number or birth certificate number just because you feel like it? No! The record ID is the birthmark. Even if the machine name changes, or the supervisor changes, the ID stays the same forever."

Cause & Effect Breakdown

What Happens When You Pick the Wrong Data Type?

Real technical failures that occur inside Power Apps when citizen developers pick lazy data types.

Failure 1: Alphabetical Sorting Trap

Text vs. Number in Comparisons

You store RepairCost as Text. A ticket costs $120, and another costs $80.

As Text: "120" < "80" = True! (Computers compare '1' against '8')
As Number: 120 < 80 = False! (Mathematical comparison works)
Disaster: High-cost repairs bypass executive approval!
Failure 2: The Slashed Date Trap

Text vs. Date/Time

You store IncidentDate as free text. Operators enter dates differently.

As Text: "04/05/2026" vs "05/04/2026" (Is it May 4th or April 5th?)
As Date/Time: DateDiff(Now(), IncidentDate, Hours) (Calculates exact SLA downtime)
Disaster: Cannot calculate machine downtime or SLA breach!

Technical Cause & Effect (55:00 – 60:00)

Explain alphabetical sorting: "Why does `"120"` evaluate as less than `"80"` in text mode? Because text sorting looks at the first letter, and `'1'` comes before `'8'` in the alphabet! That is why you NEVER store numbers as text."

Pitfalls to Avoid

4 Dangerous Mental Misconceptions & Trainer Corrections

Preempting the most frequent data design errors committed by citizen developers.

Wrong Mental Model 1

"Text is best because it gives the user maximum freedom to type anything."

The Trainer's Correction

Freedom for the user is chaos for the system. A database is a calculation engine. Free text makes sorting, filtering, summing, and automation impossible.

Wrong Mental Model 2

"Status is just a text label that the technician updates when they feel like it."

The Trainer's Correction

Status is the steering wheel of the application. It controls which buttons appear and who owns the step. If spelling varies by a single letter, the entire workflow derails.

Wrong Mental Model 3

"We don't need an ID column; we can just search by machine name or date."

The Trainer's Correction

Press #4 can break three times in one week. An auto-generated Unique ID is the permanent birthmark that links purchase orders, technician logs, and audit histories without ambiguity.

Wrong Mental Model 4

"Let's put 50 columns in the table now just in case someone needs them in the future."

The Trainer's Correction

Every field requires maintenance, validation, and screen real estate. Only create fields that directly answer a question in the active process flow.
