Workplace Crisis Case Study

The $38,000 "1-Screen Dashboard Nightmare" & The Shattered Mold

What happens when you cram an entire multi-person workflow onto a single cluttered screen.

Month 1
The "All-In-One" Screen: A junior citizen developer built an app by putting all 8 fields, 6 dropdowns, and 8 buttons onto one giant screen so users "wouldn't have to switch pages."
10:15 AM
The Greasy Finger: Operator Sothea had grease on her work gloves. She wanted to log a jittering clamp on Press #2. She tapped near the blue "Submit" button.
10:16 AM
The Accidental Click: Right next to "Submit", the developer had placed a green "Supervisor Final Sign-Off & Release" button. Her glove tapped the sign-off button on an open ticket for Press #7!
11:00 AM
The Catastrophe: Technician Dara saw the screen say "Approved & Released: Mold Die 44B Ready for Press #2". He loaded a $38,000 custom automotive die onto Press #2 (which was misaligned). On the first 400-ton stroke, the misaligned clamp completely shattered the $38,000 mold!
$38,000 Loss

The Root Architectural Failure

The developer thought: "A single screen is simpler and saves time."

⚠️ Cramming multiple roles onto one screen creates an operational minefield where critical approval actions sit inches away from routine data entry!
The Architectural Fix:

Never build a monolithic screen. Follow the "Workstation Principle": The operator gets an Intake Screen with only report fields; the supervisor gets an Approval Screen; the technician gets a Work Screen. If you don't need a button to do your task right now, that button must not exist on your screen!

Trainer Storytelling Protocol (10:00 – 16:00)

Tell this story with dramatic intensity. Ask: "Has anyone ever seen an app or website with 40 buttons on one page, and you were terrified of clicking the wrong one?" Everyone will nod. Explain: This is why professional apps separate tasks into dedicated screens.

The Airport Terminal

Sequential Physical Stations

An airport doesn't do check-in, security, and boarding in one giant room.

  • Station 1 (Check-in Kiosk): Task: print boarding pass. Only passport inputs visible.
  • Station 2 (Security Gate): Task: screen baggage. Only scan actions visible.
  • Station 3 (Boarding Gate): Task: board aircraft. Only seat number & door active.
The Bank ATM
🏧

Focused Single-Task Screens

An ATM guides you through distinct, focused steps.

  • Screen 1: Enter 4-digit PIN (Nothing else visible).
  • Screen 2: Select transaction (Withdraw, Balance).
  • Screen 3: Select amount ($20, $50, $100).
  • Screen 4: Take card & cash (Feedback confirmation).
The Core Golden Rule
🎯

The Golden UI Law

One Screen = One Human Task.

  • A screen is not an art canvas; it is a physical workstation.
  • Expose only the data needed to perform this specific task.
  • Keep action buttons relevant to the active user role.

UI Element Categorization

The 3 Core Control Families: Input, Display & Action

Every single control inside Power Apps belongs to one of three functional families. Never confuse their roles.

Family 1: Input Controls

Writing Data to the App

Controls that let a human give information to the system. Must match Day 11 Data Types.

  • TextInput ➔ Short & Long text descriptions
  • Dropdown / ComboBox ➔ Choice columns (Machine list)
  • DatePicker ➔ Scheduled maintenance dates
  • Toggle / Checkbox ➔ Yes/No boolean states
Purpose: Capture human input cleanly
Family 2: Display Controls

Reading Data from the App

Controls that are read-only. They show data without allowing accidental edits.

  • Label ➔ Titles, instructions, field names
  • HTML Text / Badge ➔ Colored status indicators
  • Gallery (`gal`) ➔ Scrollable list of cards/records
  • Image ➔ Machine schematics, equipment photos
Purpose: Present facts clearly & safely
Family 3: Action Controls

Triggering Work & Flow

Controls that execute Power Fx logic, submit forms, or navigate to other rooms.

  • Button ➔ Primary triggers ("Submit", "Approve")
  • Icon ➔ Back arrows, search magnifying glass, refresh
  • Timer ➔ Auto-refresh feeds, countdown clocks
Purpose: Cause actions & state changes

Control Families Explanation (30:00 – 35:00)

Ask the class: "If you want a supervisor to view an incident report, should the description be in a Text Input or a Label?" Answer: A Label! Because if it's in a Text Input, the supervisor might accidentally delete words while reading it!

Without navigation, users get trapped in rooms. Without feedback, users feel anxious and submit duplicate tickets.

Green banner & return

The Standard Submission & Feedback Formula Chain:
// 1. Save data, show success banner, and return home with a fade transition
btnSubmit.OnSelect =
  SubmitForm(frmNewRequest);
  Notify("Maintenance ticket created successfully!", NotificationType.Success);
  Navigate(scrHome, ScreenTransition.Fade)

// 2. The Cancel button: discard changes safely without saving
btnCancel.OnSelect = ResetForm(frmNewRequest); Back(ScreenTransition.Fade)
Crucial UX Rule: Always give the user an escape hatch! Every screen must have a clear "Cancel" or "Back" icon so users never feel trapped.

Feedback & Navigation Protocol (35:00 – 40:00)

Highlight the semi-colon chain: In Power Fx, we separate sequential actions with a semi-colon `;`. Notice how line 1 saves the data, line 2 fires the notification banner, and line 3 changes the screen. It is an exact sequence of human events.

90% of all successful business apps are built using these four universal screen archetypes.

Screen 1

`scrBrowse` (Dashboard)

Scrollable card gallery showing all active tickets, with search and status filter chips.

• Controls: Gallery, Search Box, New Button • User Task: Find my ticket & check state
Screen 2

`scrNewRequest` (Intake)

Clean data entry form with required field validation. Used by operators on the plant floor.

• Controls: Dropdowns, Text Inputs, Submit Button • User Task: Log a broken machine
Screen 3

`scrDetail` (Inspection)

Read-only view showing full incident history, timestamps, and technician repair notes.

• Controls: Labels, Status Badges, Back Arrow • User Task: Inspect historical facts safely
Screen 4

`scrApproval` (Action Gate)

Decision screen with read-only cost summary and big Approve/Reject buttons for managers.

• Controls: Cost Input, Approve/Reject Buttons • User Task: Make governance decision

Cause & Effect Breakdown

What Happens When You Break Screen Discipline?

Real operational failures that occur inside factories when citizen developers design poor user interfaces.

Trap 1: The Monolithic Screen Trap

Putting Everyone on One Screen

Operator, supervisor, and technician all share one giant screen with 25 text inputs and 6 buttons.

Consequence: Cognitive Overload & Misclicks: Operators accidentally click supervisor approval buttons, releasing uninspected machines into production.
Disaster: Broken governance, bypassed inspections, equipment damage!
Trap 2: The Silent Submit Trap

Missing User Feedback (`Notify`)

The user clicks "Submit", the button flashes, but no confirmation message appears on the screen.

Consequence: User Uncertainty & Duplication: The operator assumes the app crashed or froze. They tap "Submit" 4 more times, creating 4 duplicate repair orders.
Disaster: Duplicate tickets, technician confusion, bloated database!

Design Traps Protocol (55:00 – 60:00)

Guided Learner Practice

Spot the 4 Fatal UI Flaws in This Single-Screen Warehouse App

Examine this proposed screen wireframe created by an untrained builder. Can you identify all 4 UX violations?

Screen Element Proposed Implementation Current State The Hidden Fatal Flaw
Delete Button Giant Red "Delete All" next to Save Always active ❌ Flaw 1: No confirmation dialog; catastrophic accidental data loss!
Cost Field Editable Text Box on Browse Screen Editable by all ❌ Flaw 2: Anyone browsing tickets can accidentally modify the budget!
Cancel Button Missing completely No back arrow ❌ Flaw 3: User is trapped with no escape hatch if they change their mind!
Submit Action Saves data with zero popup or banner Silent submit ❌ Flaw 4: User assumes app froze and clicks submit 5 times (duplicates)!

The 4 Professional UI Corrections:

  • 1. Separate Destructive Actions: Move Delete behind an admin-only confirmation popup.
  • 2. Use Display Controls for Browse: Browse screen must use read-only Labels, never editable inputs.
  • 3. Provide Universal Escape: Every screen must have a Back arrow executing Back().
  • 4. Mandatory Feedback: Always invoke Notify("Success", NotificationType.Success).

Pitfalls to Avoid

4 Dangerous Mental Misconceptions in Screen Design

Preempting the most frequent UI/UX blunders committed by beginner citizen developers.

Wrong Mental Model 1

"A Power App is just one big webpage; putting everything on one screen saves clicks."

The Trainer's Correction

One screen creates cognitive paralysis and security vulnerabilities. Separate screens act as distinct rooms, keeping users focused strictly on their specific task.

Wrong Mental Model 2

"Color is just decoration; let's make all buttons and cards bright neon colors."

The Trainer's Correction

In industrial apps, color is semantic communication. Red means Danger/Stop; Green means Success/Safe; Amber means Caution. Decorative color creates visual noise and misses emergency alarms.

Wrong Mental Model 3

"Users don't need confirmation messages; they will know it worked when the screen changes."

The Trainer's Correction

Silence breeds anxiety. Without a green Notify() banner, users assume the app froze and tap submit multiple times, creating costly duplicate records.

Wrong Mental Model 4

"I should make all text boxes editable on the detail screen so users can fix typos anytime."

The Trainer's Correction

Detail screens must be read-only Display Controls (Labels). Editable boxes allow accidental keystrokes while scrolling on mobile devices to silently overwrite historical audit data.

Misconception Review (73:00 – 75:00)

Read through each misconception with humor and empathy. Say: "We have all wanted to use 10 different colors on a screen. Now you know why enterprise UI guidelines restrict colors strictly to meaningful signals."
